## Method

- **Lab:** attacker `10.77.0.2` -> victim `10.77.0.10`; run on 2026-11-09T07:05:57; Linux-6.18.44-fc-v310-x86_64-with-glibc2.39; tool versions:
  - nmap: Nmap version 7.94SVN ( https://nmap.org )
  - masscan: Masscan version 1.3.2 ( https://github.com/robertdavidgraham/masscan )
  - hping3: hping3 version 3.0.0-alpha-2 ($Id: release.h,v 1.4 2004/04/09 23:38:56 antirez Exp $)
  - fping: fping: Version 5.1
  - tcpdump: tcpdump version 4.99.4
- **Capture point:** `tcpdump` on the attacker's lab interface, one PCAP per scenario. Each PCAP is replayed through the real pyshark/tshark pipeline, with a fresh analyzer per scenario.
- **Ground truth:** `run_lab.py` records the command, its start/end time and the detectors it should trigger. *Detected* means at least one alert of an expected type; *first alert* is measured from the command's start.
- **Background traffic:** one ping per second to the victim runs throughout, standing in for the traffic a real network always has. The sensor's clock is packet-driven, so a probe that has to outlive the half-open grace period is only declared failed once a later packet arrives.
- **Host sweeps:** on a flat Ethernet segment, probes to dead hosts stop at ARP and never become IP packets. The sweep range is therefore given static neighbour entries pointing at a MAC nobody owns, which is how a routed sweep looks to the sensor (IP packets leave, nothing answers). ARP-level sweeps are not detected by this sensor.
- **Limits of this evaluation:** one lab, one victim OS, a handful of tools, short benign scenarios. Treat it as a regression and sanity benchmark, not a statement about production networks.
